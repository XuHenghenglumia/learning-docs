# 写作风格细则

面向学习的中文技术文档写作规范。目标读者是"聪明但不熟悉该领域"的工程师。

## 1. 递进原则（最重要）

任何概念按三层递进展开，顺序不可颠倒：

1. **直觉层**：比喻或生活化类比，让读者"哦，就是那个东西"；
2. **实例层**：真实产品/真实代码中的具体例子（带来源）；
3. **形式层**：精确的定义、公式、源码机制、参数细节。

反例：开场就给抽象定义。正例：先讲"银行金库不靠柜员自觉"，再引出非干扰性的数学定义。

## 2. 结构手法

- **对比必用表格**：两个以上方案/产品/机制并列时，维度做成列。
- **选型必给决策树**：以"你的场景是什么？"开头的分支伪代码。
- **复杂结构画 ASCII 图**：层级图、数据流图用代码块画，不依赖外部图片。
- **每章开头一句话预告**本章回答什么问题；结尾不重复正文，只留钩子或小结。
- **数字要带单位与出处**：性能数字注明"常见量级，随负载浮动"。

## 3. 语言规范

- 正文中文；术语首次出现保留英文原词，如"可信计算基（TCB）"。
- 不使用"简单来说"堆叠超过一次——说明前面的解释失败了，重写它。
- 避免营销语气（"强大""颠覆"），改用具体陈述（"把启动时间从 X 降到 Y"）。
- 承认不确定性：没查证到的写"据公开资料/待确认"，不编造。

## 4. 引用与事实纪律

- 关键论断标注来源（官方文档 > 源码 > 工程博客 > 第三方分析）。
- 来源之间冲突时：以官方文档/源码为准，并在文中注明差异及核实过程。
- 章末汇总参考链接列表。

## 5. 项目讲解型附加规则

- 讲代码必须带 `路径:行号`，且引用的片段控制在 15 行以内，超出则只引用核心部分并描述上下文。
- "开发思路"章节优先从 git history、issue 讨论、README 的设计说明中找动机，而不是事后推测。
- 每讲完一个机制，给读者一个"动手验证"的小实验（一条命令能看到对应行为）。
